# Postgres làm job queue với `FOR UPDATE SKIP LOCKED`

**Area:** Backend (queues, concurrency, DB)

## What it is
- `SELECT ... FOR UPDATE SKIP LOCKED` khóa các row được chọn và **bỏ qua** row đang bị transaction khác khóa, thay vì chờ.
- Nhiều worker có thể cùng "lấy việc" từ một bảng `jobs` mà không giẫm chân nhau và không block nhau.
- Có từ PostgreSQL 9.5.

## Why it matters
- Bạn đã có Postgres (Prisma) — không cần thêm Redis/RabbitMQ cho các job nhỏ đến vừa (gửi email, webhook, outbox).
- Job được enqueue **cùng transaction** với dữ liệu nghiệp vụ → không mất event (transactional outbox).
- Tránh lỗi kinh điển: 2 worker xử lý cùng một job, hoặc worker chờ lock làm tắc cả hàng đợi.

## Example
```sql
CREATE TABLE jobs (
  id         bigserial PRIMARY KEY,
  payload    jsonb       NOT NULL,
  status     text        NOT NULL DEFAULT 'pending', -- pending | done | failed
  run_at     timestamptz NOT NULL DEFAULT now(),
  attempts   int         NOT NULL DEFAULT 0
);
-- Partial index: chỉ index job còn chờ → nhỏ và nhanh
CREATE INDEX jobs_pending_idx ON jobs (run_at) WHERE status = 'pending';

-- Worker: lấy tối đa 10 job trong 1 transaction
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- ... xử lý ...
UPDATE jobs SET status = 'done' WHERE id = ANY($1);
COMMIT;
```
Với Prisma (interactive transaction + raw query):
```ts
await prisma.$transaction(async (tx) => {
  const jobs = await tx.$queryRaw<{ id: bigint; payload: unknown }[]>`
    SELECT id, payload FROM jobs
    WHERE status = 'pending' AND run_at <= now()
    ORDER BY run_at LIMIT 10
    FOR UPDATE SKIP LOCKED`;
  for (const j of jobs) await handle(j);
  await tx.$executeRaw`UPDATE jobs SET status='done' WHERE id = ANY(${jobs.map(j => j.id)})`;
});
```
Lưu ý: `id` là `bigint` nên Prisma trả về `BigInt`; `$queryRaw` dạng tagged template tự tham số hóa (an toàn SQL injection).

## Trade-offs / when NOT to use
- Giữ transaction mở suốt thời gian xử lý → job chạy lâu (phút) giữ connection và lock; nên dùng pattern "claim" (UPDATE status='running', locked_at) rồi commit sớm, kèm cơ chế reclaim job bị treo.
- Throughput bị giới hạn bởi Postgres; hàng nghìn job/giây, fan-out, pub/sub, delay phức tạp → dùng broker thật (RabbitMQ, Kafka, SQS).
- Thứ tự chỉ gần đúng: SKIP LOCKED cho một "inconsistent view" có chủ đích, không dùng cho truy vấn cần kết quả đầy đủ.
- Bảng churn cao → cần autovacuum tốt, xóa/partition job cũ.
- Cần retry/backoff, dead-letter: tự viết (`attempts`, `run_at = now() + backoff`).

## Thử trong 15 phút
1. `docker compose` chạy `postgres:16`, tạo bảng `jobs` ở trên và insert 1000 row.
2. Mở 2 terminal `psql`, cùng `BEGIN; SELECT ... LIMIT 5 FOR UPDATE SKIP LOCKED;` — terminal 2 nhận 5 row *khác*. Thử bỏ `SKIP LOCKED` để thấy nó bị block.
3. Viết worker NestJS nhỏ (`@Interval`) dùng đoạn Prisma ở trên, chạy 2–3 replica bằng `docker compose up --scale worker=3`, kiểm tra không job nào chạy 2 lần.
4. `EXPLAIN` truy vấn để xác nhận dùng `jobs_pending_idx`.
