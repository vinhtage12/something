# `CREATE INDEX CONCURRENTLY` và cái bẫy index `INVALID`

**Area:** Tricks and gotchas (Postgres / Prisma)

## What it is
- `CREATE INDEX` thường khoá bảng chống ghi (INSERT/UPDATE/DELETE bị chặn) trong suốt thời gian build.
- `CREATE INDEX CONCURRENTLY` build index mà vẫn cho phép ghi, đổi lại phải quét bảng 2 lần và chờ các transaction cũ kết thúc.
- Nếu build thất bại (deadlock, vi phạm unique...), Postgres để lại một index `INVALID`: query bỏ qua nó nhưng mỗi lần ghi vẫn tốn thêm chi phí cập nhật.

## Why it matters
Thêm index trên bảng lớn đang chạy production bằng lệnh thường có thể làm treo mọi request ghi trong vài phút. Ngược lại, dùng `CONCURRENTLY` mà không kiểm tra kết quả có thể để lại index "rác" làm chậm ghi mà không ai biết.

## Example
```sql
-- 1 statement duy nhất, KHÔNG nằm trong transaction block
CREATE INDEX CONCURRENTLY idx_orders_user_created
  ON orders (user_id, created_at DESC);

-- Tìm index INVALID sau khi build
SELECT c.relname
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE NOT i.indisvalid;

-- Khắc phục: drop rồi tạo lại (cách docs khuyến nghị)
DROP INDEX CONCURRENTLY idx_orders_user_created;
-- hoặc rebuild tại chỗ:
REINDEX INDEX CONCURRENTLY idx_orders_user_created;
```
Với `REINDEX CONCURRENTLY` thất bại: index mới có hậu tố `_ccnew` thì `DROP INDEX` rồi chạy lại; hậu tố `_ccold` nghĩa là rebuild đã thành công và chỉ cần drop index cũ.

## Trade-offs / when NOT to use
- Chậm hơn và tốn I/O hơn (2 lần quét, chờ transaction cũ). Một transaction chạy rất lâu sẽ làm build bị kẹt.
- Không chạy được trong transaction block, nên không gói chung với các statement khác trong một transaction.
- Bảng nhỏ hoặc môi trường dev/CI: lệnh thường nhanh và đơn giản hơn, không cần `CONCURRENTLY`.
- Index `UNIQUE` build concurrently: nếu dữ liệu trùng thì build fail và để lại index INVALID.

## Thử trong 15 phút với stack của bạn
1. `docker compose up -d postgres`, tạo bảng `orders` rồi `INSERT ... SELECT generate_series(1, 2000000)`.
2. Terminal A: chạy vòng lặp `INSERT` liên tục; terminal B: `CREATE INDEX idx_x ON orders(user_id)` và quan sát INSERT bị treo. Drop index, lặp lại với `CONCURRENTLY` và so sánh.
3. Với Prisma: tạo migration trống bằng `prisma migrate dev --create-only`, tự viết SQL trong file `migration.sql`, mỗi migration chỉ chứa đúng một statement `CREATE INDEX CONCURRENTLY`. Lưu ý (tôi chưa kiểm chứng trong docs Prisma): nếu migration chứa nhiều statement, hãy tự thử xem có lỗi "cannot run inside a transaction block" không, và tách file nếu cần.
4. Với Spring Boot: Flyway có thể chạy migration ngoài transaction (`executeInTransaction=false` trong file `.conf` cùng tên) — hãy kiểm tra docs của phiên bản bạn dùng.
5. Thêm query `indisvalid` ở trên vào bước kiểm tra sau deploy.
