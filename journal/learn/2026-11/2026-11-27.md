# Transactional Outbox: ghi DB và phát event mà không mất / không lệch

**Area:** Architecture & design patterns (event-driven, resilience)

## What it is
- Thay vì "ghi DB rồi publish event" (2 hệ thống, không có transaction chung), ta ghi event vào bảng `outbox` **trong cùng DB transaction** với dữ liệu nghiệp vụ.
- Một tiến trình riêng (poller/relay) đọc bảng `outbox` và publish lên broker (Kafka/RabbitMQ/...), rồi đánh dấu đã gửi.
- Kết quả: state và event hoặc cùng tồn tại, hoặc cùng không tồn tại.

## Why it matters
- Dual write: `INSERT order` thành công nhưng publish lỗi (hoặc crash giữa chừng) → các service khác không bao giờ biết order tồn tại. Đảo thứ tự (publish trước) thì ngược lại: event "ma" cho dữ liệu đã rollback.
- Quan trọng với NestJS + GraphQL federation khi các subgraph/service đồng bộ dữ liệu qua event, hoặc Spring Boot hexagonal phát domain event ra ngoài.

## Ví dụ (Prisma + Postgres)
```prisma
model Outbox {
  id          BigInt    @id @default(autoincrement())
  aggregateId String
  type        String
  payload     Json
  createdAt   DateTime  @default(now())
  publishedAt DateTime?
  @@index([publishedAt, id])
}
```
```ts
// Ghi: cùng một transaction
await prisma.$transaction(async (tx) => {
  const order = await tx.order.create({ data: dto });
  await tx.outbox.create({
    data: { aggregateId: order.id, type: 'OrderCreated', payload: { id: order.id } },
  });
});
```
```ts
// Relay: nhiều instance chạy song song vẫn an toàn nhờ SKIP LOCKED
await prisma.$transaction(async (tx) => {
  const rows = await tx.$queryRaw<{ id: bigint; type: string; payload: any }[]>`
    SELECT id, type, payload FROM "Outbox"
    WHERE "publishedAt" IS NULL
    ORDER BY id LIMIT 100
    FOR UPDATE SKIP LOCKED`;
  for (const r of rows) await broker.publish(r.type, r.payload);
  await tx.$executeRaw`UPDATE "Outbox" SET "publishedAt" = now()
    WHERE id = ANY(${rows.map((r) => r.id)})`;
});
```
Lưu ý: nếu publish xong mà crash trước khi commit, event sẽ được gửi lại → **at-least-once**.

## Trade-offs / khi KHÔNG dùng
- Consumer **phải idempotent** (dedupe theo `id` của outbox, ví dụ bảng `processed_events`).
- Thứ tự chỉ được đảm bảo trong phạm vi một lần poll/một aggregate nếu bạn cẩn thận (partition key = aggregateId); chạy nhiều relay song song với SKIP LOCKED có thể làm lệch thứ tự giữa các batch.
- Thêm độ trễ (chu kỳ poll) và tải ghi lên DB; cần job dọn bảng (xóa/partition các dòng cũ).
- Không cần nếu: chỉ ghi một hệ thống, hoặc chấp nhận mất event thỉnh thoảng (log/analytics). Cân nhắc CDC (Debezium đọc WAL) thay cho polling khi throughput lớn.

## Thử trong 15 phút
1. Thêm model `Outbox` vào Prisma schema, `prisma migrate dev`.
2. Sửa một use case (vd. tạo order) ghi outbox trong `$transaction`.
3. Viết `@Cron`/`setInterval` trong NestJS chạy đoạn relay, publish tạm bằng `console.log`.
4. Chạy 2 instance (docker compose `--scale`), kiểm tra không có event nào bị log 2 lần; thử `throw` sau publish để thấy retry.

## Nguồn tham khảo
Mình **không mở được** nguồn nào trong lần chạy này (sandbox chặn mạng ra ngoài), nên không liệt kê link như đã xác minh. Nên đọc để đối chiếu:
- microservices.io — pattern "Transactional outbox" (Chris Richardson)
- PostgreSQL docs — `SELECT` → "The Locking Clause" (`FOR UPDATE ... SKIP LOCKED`)

Cú pháp `FOR UPDATE SKIP LOCKED` và Prisma `$transaction`/`$queryRaw` ở trên chưa chạy thử thực tế; hãy kiểm tra với phiên bản Prisma của bạn.
